The new attack surface

Your IDE just became part of the worm.  

The campaign writes payload files into .claude/ and .vscode/ directories of every repository it can reach. Cloning a poisoned repository and opening it in your AI coding assistant re-fires the entire attack on a fresh machine.

This is the structural shift. For most of 2025, the AI coding assistant and the IDE workspace were treated as productivity surfaces — adjacent to the supply chain risk, but not part of it. The April 2026 wave changes that. The campaign deliberately writes attacker-controlled files into the configuration directories that AI coding assistants and IDEs treat as implicitly trusted at session start.

What the campaign drops, and what each file does:

.claude/settings.json Claude Code SessionStart hook — runs node .vscode/setup.mjs on every new session
.claude/setup.mjs Bun bootstrapper — downloads the runtime, prepares the payload
.claude/router_runtime.js Self-copy of the running payload via Bun.main
.vscode/tasks.json VS Code task Environment Setup — runs on folderOpen
.vscode/setup.mjs Identical dropper — entry point for the VS Code execution path

The commits are authored as claude <claude@users.noreply.github.com> with the message chore: update dependencies — designed to blend into normal developer activity in any repository's history.

The mechanical effect is that the persistence outlives the package. Once an organisation removes a malicious version of @cap-js/sqlite or lightning from its lockfiles, the attack chain is not over — every repository the compromised developer's tokens could touch may now carry a payload that re-fires the next time anyone clones that repository and opens it in Claude Code or VS Code. This is the worm continuing to propagate through the developer's tooling rather than through the package registry.

The credential targets reflect the same shift in posture. Among the secrets the payload harvests are MCP configuration files and Claude config — explicit acknowledgement that the AI coding assistant's own context is now considered worth stealing. SANDWORM_MODE earlier in 2026 demonstrated prompt-injection logic targeting AI coding assistants directly. The trajectory is clear, and it lands here: AI development tooling is not collateral to the supply-chain threat anymore. It is the threat surface.

The thesis of this report
How the worm works

Eight techniques. No magic.  

What looks like an advanced operation is a careful composition of well-known techniques against a software supply chain not designed to resist them. Each technique is individually catalogued in MITRE ATT&CK; each is individually defensible.

T1195.002
Compromise software dependencies
Initial Access
The publishing surface of a legitimate, widely-trusted package becomes the delivery vehicle. npm install, pip install, and composer install carry the payload to every machine that pulls an affected version.
The OIDC trusted-publisher policy for @cap-js/sqlite trusted any workflow in cap-js/cds-dbs, not only the canonical release-please.yml on main. A workflow on a non-main branch with id-token: write permission and environment: npm reference could exchange an OIDC token on behalf of the package. For mbt, an npm token (CLOUD_MTA_BOT_NPM_TOKEN) was likely exposed via a misconfigured CircleCI pull-request job. The Lightning, intercom-client, and intercom-php compromises chained from a single developer's local install of pyannote-audio, which pulled the compromised lightning as a transitive dependency on that workstation, providing the credentials to attack the Intercom packages.
T1059.007 / T1059.006
Install equals execution
Execution · JavaScript / Python
The bootstrappers run automatically during dependency installation, before any application code. setup.mjs via npm preinstall; setup-intercom.sh via Composer plugin events; start.py via PyPI __init__.py daemon thread.
The bootstrapper downloads Bun 1.3.13 from github.com/oven-sh/bun/releases, extracts the platform-specific binary, and uses Bun rather than Node to execute the main payload. The Lightning variant injects directly into __init__.py via threading.Thread daemon — the payload runs the moment any code imports the package, not just during install. The structural lesson: install equals execution. Cancelling the install does not undo the exfiltration, which completes in seconds.
T1552.001
Credentials in files
Credential Access
A directed sweep of well-known credential locations: .npmrc, .pypirc, .git-credentials, ~/.ssh/, .env, AWS/Azure/GCP files, Docker stores, Kubernetes config, Vault tokens, MCP and Claude configuration files, shell histories, browser password stores.
The Lightning variant adds cryptocurrency wallets (Bitcoin, Litecoin, Monero, Dogecoin, Dash, Exodus, Atomic, Ledger), VPN credentials (NordVPN, ProtonVPN, CyberGhost, Windscribe, OpenVPN), Discord and Slack session data. The SAP-operation variant adds extraction of saved passwords from Chrome, Safari, Edge, Brave, and Chromium. The harvest list documents the present-day reality: every one of these is a credential at rest in a known location on a developer machine.
T1552.005
Cloud instance metadata
Credential Access
Where the payload runs in a cloud workload, it queries the instance metadata service (IMDS) directly for workload identities and short-lived credentials. Authenticated calls against AWS SSM, AWS Secrets Manager, Azure Key Vault, GCP Secret Manager, Kubernetes Secrets, Vault.
Supports VM, serverless, and container workloads — Google Cloud Functions, Amazon ECS, Kubernetes pods. This pattern was already established in Shai-Hulud 2.0 in November 2025 and continues unchanged. The token has limited lifetime, but the active session is enough to pivot.
T1212
Runner memory scraping
Credential Access
On Linux CI runners, an embedded Python helper reads /proc/<pid>/maps and /proc/<pid>/mem for the Runner.Worker process, extracting every secret matching the GitHub Actions in-memory secret structure.
This bypasses GitHub Actions' own log-masking guarantee — secrets that are masked when echoed to logs are still extractable from the running worker's address space. This technique was observed in earlier TeamPCP campaigns and continues in the SAP wave. The countermeasure is workload-level isolation, not log-masking.
T1027
Obfuscated payload
Defense Evasion
An ~11.6-11.7 MB obfuscated single-file JavaScript bundle (router_runtime.js / execution.js). C2 hostname reconstructed from decoded blobs at runtime. Stolen credentials wrapped with AES-256-GCM and RSA-OAEP/SHA-256 before transit.
Executing under Bun rather than Node is a complementary evasion: detection rules looking for credential access spawned from node will not see Bun spawning the same code. The Bun binary self-deletes after execution to reduce forensic traces. Wiz's TeamPCP attribution rests on the shared RSA public key across operations.
T1567.001
Exfiltration via GitHub
Exfiltration
The dominant channel is GitHub itself. The malware creates a public repository on the victim's own GitHub account, names it with a Dune-themed slug, sets the description to A Mini Shai-Hulud has Appeared, and commits the encrypted payload there.
Cross-victim exfiltration was confirmed in Shai-Hulud 2.0 — one victim's secrets observed in a public repository owned by a second, unrelated victim — meaning organisations auditing only their own GitHub identities can miss exfiltrated data. The fallback channel is also GitHub: the payload searches public commits for the keyword beautifulcastle to retrieve a base64-encoded current exfiltration endpoint, allowing the attacker to rotate infrastructure without publishing a new package version. Blocking github.com is not a realistic option for development teams.
T1546
IDE / AI-assistant persistence
Persistence
The payload writes files to .claude/router_runtime.js, .claude/setup.mjs, .claude/settings.json (Claude Code SessionStart hook), .vscode/setup.mjs, .vscode/tasks.json (VS Code runOn: folderOpen task) — turning the AI coding assistant and the editor into the persistence surface.
Commits authored as claude <claude@users.noreply.github.com> with the message chore: update dependencies, blending into normal developer activity. Any developer who clones the repository and opens it in VS Code or Claude Code re-triggers the dropper on a fresh machine. This is the mechanism that makes the campaign continue to spread even after the original poisoned packages have been removed from the registries — turning the developer's tooling itself into the persistence and re-distribution channel.
T1195.001 · Initial Access
Compromise software tools
The April 22 Bitwarden cascade was a Dependabot pull of a compromised checkmarx/kics:latest image into Bitwarden's CI/CD pipeline — one developer tool poisoning another developer tool's pipeline through ordinary dependency-update automation.
T1078.004 · Initial Access / Lateral Movement
Valid accounts (cloud)
OIDC token exchange against registry.npmjs.org/-/npm/v1/oidc/token/exchange/package/ — using a valid (mis-scoped) cloud-issued credential to publish on behalf of a package the attacker does not own.
T1098 · Persistence (registry-level)
Account manipulation
With a harvested npm_ token, the payload calls /-/whoami and package APIs, enumerates packages the token can write to, then downloads, patches (re-injecting setup.mjs + payload, setting scripts.preinstall, bumping the patch version), and republishes the trojanized tarball.
T1480 · Defense Evasion
Execution guardrails — Russian-locale kill switch
The payload inspects system date/time locale and language environment variables; if any value begins with ru, it terminates without exfiltration. Same guardrail observed in earlier TeamPCP Checkmarx and Bitwarden operations — one of the technical signatures supporting the TeamPCP attribution.
T1102.002 · Command and Control
Web service — bidirectional
The payload queries the GitHub commit-search API for the keyword beautifulcastle to retrieve a base64-encoded current exfiltration endpoint, and EveryBoiWeBuildIsAWormyBoi / OhNoWhatsGoingOnWithGitHub to recover stolen tokens for fallback exfiltration. GitHub's public commit search functioning as a dead-drop resolver.
T1070.004 · Defense Evasion
Indicator removal — file deletion
The Bun binary self-deletes after the payload executes, reducing on-disk forensic indicators. The lock file /tmp/tmp.987654321.lock is one of the few stable artifacts left behind on Linux hosts.
T1485 · Impact (lineage only)
Data destruction (Shai-Hulud 2.0 fallback)
The November 2025 Shai-Hulud 2.0 wave introduced a fail-closed fallback that wiped the user's home directory if it could not authenticate using GitHub or npm credentials. Whether this destructive fallback is retained in the April 2026 Mini variants is not explicitly confirmed in current public reporting.

Where the controls live now

The pipeline is the perimeter, not the application.  

OWASP's Top 10 for CI/CD Security Risks names nine of the ten categories this incident exemplifies. The incident is not exotic. It is a textbook reading of a framework that already exists.

CICD-SEC-1
Insufficient flow control mechanisms
Primary driver
For the @cap-js/* packages, the npm OIDC trusted-publisher configuration trusted any workflow in cap-js/cds-dbs, not only the canonical release-please.yml on main. A push of a workflow with id-token: write permission and environment: npm reference on any branch could exchange an OIDC token on behalf of the package. The post-incident addition of a human-approval gate to npm publication closes this surface.
CICD-SEC-2
Inadequate identity and access management
Primary driver
A single credential with broader publish or workflow rights than its narrowest legitimate use case becomes the exact key that propagates the worm. Static publish tokens, GitHub PATs with workflow scope, OIDC trust relationships that were over-broad at the workflow level — each is a category of identity boundary that the campaign found and crossed.
CICD-SEC-3
Dependency chain abuse
Primary driver
Three install-time execution paths in parallel: npm preinstall hooks (SAP packages, intercom-client), Composer post-install-cmd/post-update-cmd plugin events (intercom-php), PyPI __init__.py injection that runs at first import (lightning). The Packagist case additionally relied on Git tag mutability — Packagist mirrors upstream Git tags, and tags can be force-updated, so an attacker who can modify the upstream repository can replace the contents of an existing version without changing the version number.
CICD-SEC-4
Poisoned pipeline execution
Primary driver
A misconfigured CircleCI pull-request job in SAP/cloud-mta-build-tool listed redacted project secrets — including CLOUD_MTA_BOT_NPM_TOKEN, CLOUD_MTA_BOT_GITHUB_TOKEN, CircleCI OIDC tokens, Docker Hub credentials, Cloud Foundry credentials — to a job triggered from an external branch. Octokit warnings for POST https://api.github.com/user/repos in the same logs match the malware's GitHub exfiltration behaviour. This is a category of misconfiguration that affects every CI provider, not a single-organisation issue.
CICD-SEC-5
Insufficient pipeline-based access controls
Primary driver
The OIDC token issued for an @cap-js build was usable to publish to npm because the trust policy did not pin the workflow file path or branch. The CI runner secrets that ended up in /proc/<pid>/maps for Runner.Worker were available to a process that should not have been there at all. Pipelines hold release-tier authority continuously, when in most cases they need it for a single job.
CICD-SEC-6
Insufficient credential hygiene
Primary driver
Long-lived static tokens were the alternative to OIDC trusted publishing — the very weakness GitHub's post-Shai-Hulud guidance was designed to retire. On the developer side, the harvest list documents the reality: .npmrc, .pypirc, .git-credentials, ~/.ssh/, .env, AWS/Azure/GCP credential files, Docker stores, Kubernetes config, Vault tokens, MCP and Claude configuration files, shell histories, browser password stores. Every one is a credential at rest in a known location on a developer machine.
CICD-SEC-7
Insecure system configuration
Contributing
Defaults across the major package managers permit lifecycle scripts to run by default. npm install runs preinstall, Composer plugins run post-install-cmd, pip install runs whatever is in a package's setup.py or __init__.py. None of these defaults is a vulnerability in the registry; they are configuration choices the consuming organisation can override but typically does not.
CICD-SEC-8
Ungoverned use of third-party services
Contributing
GitHub itself is the third-party service being abused — for delivery (Bun runtime download from GitHub Releases), exfiltration (public repository creation under the victim's account), and command and control (commit-search as a dead-drop resolver). Blocking github.com is not a realistic option for development teams, which makes GitHub's role as supply-chain infrastructure a governance question rather than a network-control question.
CICD-SEC-10
Insufficient logging and visibility
Primary driver
Several detection-degrading choices stack: Bun execution (defenders watching for credential access spawned from node see nothing), Bun binary self-deletes after execution, payloads daemonize on Linux/macOS (stdout=DEVNULL, stderr=DEVNULL), exfiltration travels over normal api.github.com traffic. Cross-victim exfiltration confirmed in Shai-Hulud 2.0 means an organisation auditing its own GitHub may miss data routed to an unrelated victim's account.
A constructive read

The controls existed. The configuration was the work.  

Trusted publishing was deployed. SCA tooling was running. EDR was watching. What separated rapid containment from extended exposure was whether the careful narrowing — trust-policy scoping, secret isolation, endpoint coverage on developer machines — had been done.

SAP's April 29 response is the operational benchmark. From malicious publish to clean superseding versions: roughly four hours. The cds-dbs team had migrated to OIDC trusted publishing in November 2025 — exactly the post-Shai-Hulud move the ecosystem needed. When the incident hit, SAP's cap-npm GitHub Actions OIDC trusted publisher was used to publish clean superseding versions at 13:46 UTC the same day. The compromised cloudmtabot token was suspended. A human-approval gate was added to npm publication immediately. Security note 3747787 was published to customers and partners.

This is what enterprise containment looks like in this category — fast clean-version publication, transparent disclosure, and structural follow-through with workflow hardening. Most organisations consuming open-source tooling would aspire to a four-hour containment window.

npm trusted publishing (OIDC-based)
Eliminates the long-lived static-token surface. A token harvested from a CI log or developer endpoint is no longer sufficient to publish — the publishing identity is bound to a specific workflow execution.

The cds-dbs team migrated to OIDC trusted publishing in November 2025 — exactly the right call coming out of the September 2025 Shai-Hulud incident. The trust policy, however, accepted any workflow in cap-js/cds-dbs rather than only the canonical release-please.yml on main. Trusted publishing closed the long-lived-token surface; the next layer of work is the trust-policy refinement.

The structural reality

Trusted publishing is not a single switch — it is a configuration with a default-permissive trust policy, and the careful narrowing is the actual security work. SAP's post-incident addition of a human-approval requirement is the structurally correct response.

Pull-request CI permission isolation
A pull-request job that cannot see release-tier secrets cannot leak them. Disrupts the initial-access path for any token-exposure vector — including the CircleCI lead in the SAP cloud-mta-build-tool incident.

The default behaviour of many CI providers is permissive in ways that surprise even careful operators. CircleCI contexts, GitHub Actions environment secrets, and Jenkins credentials bindings each require active configuration to exclude PR builds from inheriting release-tier scope. The failure mode is silent — the secrets simply appear in the logs of a job that should not have them.

Why this is hard

Least privilege at the job level is well understood in principle and routinely missed in practice because the cost of getting it right is configuration discipline distributed across every pipeline an organisation owns.

Disabling lifecycle scripts at install time
A CI runner installing dependencies with --ignore-scripts (npm) or --no-plugins (Composer) does not execute install-time hooks. Breaks the install-equals-execution assumption.

The defaults across all three ecosystems permit lifecycle-script execution, and a meaningful share of legitimate packages depend on lifecycle scripts to function (native compilation, post-install setup, CLI symlinking). Turning these off globally creates a long tail of broken installs that organisations have to triage individually. The discipline is therefore allow-list per package, which requires SBOM granularity most organisations do not yet have.

The structural read

This is one of the most powerful blast-radius reducers available, and it is structurally hard to adopt because the ecosystem grew up assuming lifecycle scripts would run. The work is the patient cataloguing of which dependencies legitimately need to run code at install and which do not.

Lockfile pinning with integrity hashes
A lockfile with explicit integrity hashes refuses to install a tarball whose contents do not match. Blocks the install path even when the registry serves a malicious version under the same number.

Lockfile pinning protects only against the specific malicious version when the legitimate version's hash is already in the lockfile. The first organisation to install a malicious version — between the malicious publish and the registry takedown — has no prior hash to compare against; their lockfile records the malicious hash as authoritative. Lockfiles are a propagation-rate limiter, not a patient-zero defence.

The four-hour window for the SAP packages and the minutes-to-hours window for Lightning, Intercom-client, and Intercom-PHP is exactly the window where lockfiles offer no protection. Lockfiles work well for the second through millionth installer; the work is to shorten the patient-zero window through registry-side scanning and behavioural analysis.

Endpoint-level package interception
A pre-install check that consults a threat-intelligence feed at the moment of npm install blocks the malicious version from ever reaching the lockfile — exactly the patient-zero window that lockfile pinning cannot cover.

Effective only where the intel feed already knows the version is malicious. Socket detected the Packagist intercom/intercom-php@5.0.2 artifact 14 minutes after release — extremely fast on the vendor side, but the first 14 minutes of installs were not protected by anything except registry-side controls that did not yet exist for this version.

This is one of the most actively evolving areas of supply-chain defence. Treating it as a maturing control rather than a finished one keeps the recommendations honest.

Cryptographic integrity sealing of AI-agent and IDE configuration files (emerging category)
A new control category responding directly to the .claude/ and .vscode/ persistence vector. Files sealed with cryptographic hashes; modifications fail verification at runtime; changes routed through human approval.

This is a newly emerging class of mitigation, responding directly to the persistence vector the April 2026 wave introduced. One open-source implementation, Agent Context Guard (Apache 2.0), seals markdown and configuration files with SHA-256 hashes and HMAC-SHA256 signatures, verifies integrity at runtime through a guarded read API, and routes any change through an agent-proposes / human-approves workflow with a tamper-evident audit log. It includes adapters for the major agent frameworks: LangChain, CrewAI, OpenAI tools, Anthropic tools, AutoGen, LlamaIndex, MCP, OpenClaw.

Disclosure

Agent Context Guard is open-source software authored by this report's author; included here as one example of an emerging tool category, not a singular endorsement. Other open-source and commercial tools in this space are likely to emerge as the threat surface continues to develop.

Why this is forward-looking

The category did not exist at scale during the April 2026 wave. This is a forward-looking mitigation rather than a missed one — included to mark that the development community is starting to build the tools the new threat surface requires. AI-agent configuration integrity is a category that did not need to exist five years ago. The fact that it now does is itself evidence of the community responding to the same shift this report names.

Treat the developer endpoint as production attack surface
A developer endpoint with EDR coverage, restricted local credential storage, and behavioural monitoring catches the Bun spawn, the long-running daemon, the unexpected outbound to zero.masscan.cloud, and the file write to .claude/ and .vscode/.

Many enterprise EDR rollouts treat developer machines as a special tier where false-positive sensitivity is high — terminal usage, compiler invocations, and developer tooling produce a lot of noise that looks adjacent to malicious behaviour. The result is often weaker policies on developer endpoints than on general corporate endpoints. The campaign exploits exactly that gap.

Developer machines have historically been treated as ergonomic terrain that security has to tread lightly across; the April 2026 wave makes the case that they hold cloud-credential, source-code, and customer-data exposure equivalent to production servers, and the policy posture has to follow.

SCA / SBOM with continuous IOC integration
Continuous scanning of dependency trees against known-bad feeds catches affected versions in lockfiles and artifact stores once IOCs are published. Elastic's December 2025 postmortem credits this stack with rapid containment of Shai-Hulud 2.0.

Same patient-zero window as lockfile pinning. Where this control performs strongly is in the second-wave defence — auditing the long tail of installations across an enterprise once IOCs are public. Elastic's case is the model: SCA tooling plus threat intel feeds plus an IR runbook produced rapid containment. The discipline is keeping the inventory continuous and the threat-intel feeds integrated.

CircleCI: restrict context access. Jenkins: segregate credentials bindings between PR and release pipelines.
  • Tighten OIDC trusted-publisher trust policies Pin to a specific workflow file, repository, and main branch. Treat any wildcard or branch-permissive trust policy as a finding equivalent to a long-lived secret in source control.
  • Adopt install-time package interception Aikido Safe Chain (open source), Socket CLI, or commercial vendor offerings. Configure to block on threat-intel feed match and log every install for retrospective hunting. Patient-zero gap remains; control is real and improving.
  • Stand up continuous monitoring for campaign markers Detection rules firing on Bun process spawn from Node-context, outbound to zero.masscan.cloud or 94.154.172[.]43, file writes to .claude/ or .vscode/ paths in repos with concurrent token use. Elastic's Shai-Hulud 2.0 detection rules are a public reference.
  • Default --ignore-scripts and --no-plugins in CI Build an explicit allow-list of dependencies that legitimately need lifecycle scripts. For PyPI, document and review every package whose __init__.py performs work beyond imports.
  • Seal AI-agent and IDE configuration files (emerging) Cryptographic integrity sealing for .claude/, .cursor/, .vscode/, .continue/, .aider/, and equivalent configuration directories. Route any agent-proposed change through human approval. Verify integrity in CI as a build-blocking check. Agent Context Guard (Apache 2.0) is one open-source implementation; disclosure: authored by this report's author. Recommended as one example of an emerging tool category.
Horizon 02 · Medium-term
1–3 months
Bring developer tooling into production posture.
  • EDR and behavioural monitoring on developer endpoints Bring developer machines into the same EDR tier as production servers. The cultural argument that developer endpoints need ergonomic latitude has to be revisited — they hold cloud-credential, source-code, and customer-data exposure equivalent to production.
  • Migrate long-lived cloud credentials to workload identity AWS IAM Roles Anywhere or IRSA / EKS Pod Identity for Kubernetes; Azure Workload Identity; GCP Workload Identity Federation; Vault dynamic secrets. Bind the issued credential to a specific audience and job scope. Highest-leverage program-level control against this category of threat.
  • Continuous SBOM with integrated threat-intel feeds The deliverable is not the SBOM artifact — it is the integration that surfaces a newly-published IOC across every place that dependency lives in the organisation within minutes. Elastic's December 2025 postmortem is the working example.
  • Vendor-review programme for security and developer tooling The campaign's pattern of targeting the tools developers are told to trust most means the assumption that security vendors are net-defenders has to be tempered with structural review. Same questions you'd ask any supplier: trusted publishing? hardened CI? disclosure SLA?
Horizon 03 · Long-term
3–12 months
Re-architect the developer trust boundary.
  • Externalise sensitive credentials from developer machines Hardware tokens for SSH and Git signing. Just-in-time cloud credentials brokered through workload-identity providers. Password managers backed by phishing-resistant MFA rather than tokens in shell rc files. The argument that has to be won at leadership level: the developer endpoint is part of the production blast radius.
  • Board-level visibility on supply-chain risk Quarterly metrics: dependency coverage by continuous SBOM scanning; CI pipelines using trusted publishing with pinned trust policies; cloud credentials in CI that are short-lived workload-identity-issued; mean time from IOC publication to organisation-wide remediation. Without this layer, the work above erodes between incidents.
  • Engage upstream with registries and consortia Registry-side malware scanning at upload time; tag-immutability on Packagist; default --ignore-scripts discussions at npm; faster mass-rotation tooling for affected maintainers; cross-registry threat-intel sharing on actor-controlled repository markers. The arc from September 2025 to today is the case for the work.
  • Commit to the cultural reframing The IDE, the AI coding assistant, the package manager, the build tool, and the registry are enterprise risk surfaces that need governance, monitoring, and incident-response coverage on the same footing as any production system. This recommendation has no discrete deliverable. Its presence or absence determines whether everything above is point fixes or a coherent programme.
The takeaway

These attacks are not over.  

AI tools are now the target. Three waves in five months — Bitwarden CLI, the SAP CAP packages, PyTorch Lightning and the Intercom client across npm, PyPI, and Packagist — show a campaign that has stopped treating developer tooling as collateral and started treating it as the primary attack surface.

These attacks are not over, and the work that closes them is not exotic: trust-policy narrowing, pipeline-secret isolation, AI-assistant configuration governance, and the cultural recognition that an IDE workspace is now part of the production blast radius.
